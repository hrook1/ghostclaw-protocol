# x402 payment flow

## Scheme

The GhostClaw scheme name is:

```text
ghostclaw-confidential-x402-v2
```

It adds confidential amount settlement to a standard x402 request and response
flow. The payer and merchant identities stay public.

## Merchant requirement

The merchant sends an x402 payment requirement through TLS. The requirement
contains the public merchant address and terms for the requested service.

The merchant also publishes a GhostClaw merchant card. The card contains:

- Base Sepolia network name.
- Merchant Base address.
- Merchant owner field.
- X25519 note encryption public key.

## Payer budget

The agent reads the quoted amount. The local runtime checks the human policy.
An allowed payment continues without a prompt. An out-of-budget payment returns
`GHOSTCLAW_BUDGET_EXCEEDED` and an approval identifier.

The wallet checks that the merchant address has the published owner field in
the Base pool.

## Request binding

The wallet hashes the exact x402 payment requirement bytes. It adds a random
256-bit salt and derives a field-safe request digest.

The circuit binds the request digest to these values:

- Private payment amount.
- Payer owner.
- Merchant owner.
- Public payer address.
- Public merchant address.
- Pool context.

The salt prevents an observer from testing a small set of likely request bodies
and amounts against the public payment intent.

The payer sends the salt only to the merchant through TLS.

## Local proof

The wallet selects one private note. It gets a depth-20 membership path from
the public event tree.

The local prover checks note ownership, membership, and value conservation. It
creates a merchant note and payer change note. The merchant output position is
private and random.

The private witness stays on the payer machine. The proof contains no readable
amount.

## Sponsored Base call

The adapter creates one `confidentialTransfer` call. The relay and Alchemy
prepare a sponsored UserOperation.

The local Base key signs the checked operation. The Base pool verifies the
proof, marks the nullifier and payment intent, appends both outputs, and emits
`X402Settlement`.

The x402 settlement event contains:

- Payment intent.
- Public payer.
- Public merchant.
- Payer owner.
- Merchant owner.
- Nullifier.
- Two output commitments.
- Pair index.
- New tree root.

It contains no payment amount.

## Payment response

After confirmation, the payer creates a payment response. It contains the Base
transaction hash, payment intent, request salt, and encrypted merchant note.

The note envelope contains a fixed-size encrypted payload. The merchant address
and payment intent are authenticated data.

The payer sends the response through the existing TLS service connection.

## Merchant verification

The merchant uses an independent Base RPC. It performs these checks:

1. Get the transaction and receipt.
2. Require a successful confirmed transaction.
3. Decode the EntryPoint and smart-account call.
4. Require the exact GhostClaw pool address.
5. Require the exact `confidentialTransfer` call.
6. Match the payer and merchant addresses.
7. Match the payment intent and public outputs.
8. Match the `X402Settlement` event.
9. Require the commitment and root in pool state.
10. Reject a payment intent already imported by this wallet.
11. Decrypt the note.
12. Recalculate its commitment and payment intent.
13. Recalculate the request digest from the original requirement and salt.
14. Import the note after every check passes.

The merchant releases the service after its confirmation policy passes.

## Client interface

The MCP server exposes `ghostclaw_fetch` and `ghostclaw_check_budget`.

The fetch tool sends the original request. It validates a `402` requirement,
creates the proof, settles on Base, and retries the exact request.

The library exports the same behavior as `fetch` from `ghostclaw`.

## Facilitator role

A facilitator performs the public settlement checks. It does not need the
payment amount to confirm that the GhostClaw transaction settled.

The merchant still needs the encrypted note to receive private value. A normal
x402 facilitator will not understand this scheme until it adds GhostClaw
verification and response fields.

The hosted route is `/facilitator/verify`. Shared rate limits protect it. The
merchant middleware still performs private note decryption and request binding
before it releases the resource.

The middleware does not send the x402 quote to the facilitator. The amount and
resource URL stay between the payer and merchant.

## Test address-report flow

The demo protects one public Base address report with the GhostClaw scheme.
The service returns a `402` requirement for 1 test gUSD.

The payer creates the proof locally. The merchant imports the encrypted note
after the facilitator confirms the public Base settlement.

The service stores a ready report job in Redis. A repeated paid request returns
the same job. The delivery URL does not start another payment.

The service can see the requested public address and the merchant note amount.
The facilitator cannot see the quote or resource URL. Base cannot see the
payment amount or private note balance.

Coinbase's standard `exact` scheme uses a public token transfer. That scheme
reveals the payer, merchant, asset, amount, and transaction time. This release
does not treat standard `exact` settlement as confidential-compatible.

## Latency

Local proof creation happens before the sponsored Base call. The reference
payment proof median is 0.783 seconds.

Relay preparation, local signing, bundler inclusion, and Base confirmation add
network time. See `docs/BENCHMARKS.md` for the observed end-to-end result.

## Privacy limits

The public chain reveals that the payer called the merchant through GhostClaw.
It also reveals the transaction time and output commitments.

The public chain does not reveal the payment amount or note balances. The
merchant learns the amount because it decrypts the received note. The payer
already knows the amount.

TLS protects the request body, salt, and note envelope during delivery. A
compromised endpoint can expose those values.
